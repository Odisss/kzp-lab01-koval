## 1. Тема, номер і варіант

- Тема: обробка даних засобами Python — CSV, колекції, функції, модулі, винятки, pytest,
  ruff, wheel.
- Варіант 11 (незмінний), предметна область «Аптека».
- Поля CSV: `name,form,price,days_left,prescription`; відбір — `days_left <= 30`;
  словник — кількість за `form`; множина — форми; звіт — найближчий термін і середня ціна.
- ОС: Windows 11, Python 3.12.6, VS Code, PowerShell.
- Репозиторій: <https://github.com/Odisss/kzp-lab01-koval>, гілка `lab06`, версія `1.5.0`,
  тег `v1.5.0`.

## 2. Мета роботи

Створити невеликий Python-пакет, який читає CSV аптеки, перетворює текстові поля на
типізовані значення, будує звіт за допомогою списків, словників і множин та записує його
в окремий текстовий файл; розділити код на модулі, обробляти помилки явно й перевірити
поведінку тестами.

Досягнутий стан: пакет `kzp_lab06` із п'ятьма модулями та CLI (`python -m kzp_lab06.cli`
і команда `kzp-lab06`), 45 тестів pytest проходять, `ruff check` і `ruff format --check`
чисті, wheel збирається, встановлюється в окреме середовище й дає той самий звіт; CI на
Ubuntu, Windows і macOS зелений. Java-частина (ЛР № 1–5) не змінювалася й продовжує
перевірятися в CI окремим job.

## 3. Формат CSV

Файл `data/lab06.csv` (UTF-8, роздільник `,`, LF):

```text
name,form,price,days_left,prescription
Парацетамол,Таблетки,45.50,420,false
Амоксицилін,капсули,132.00,25,true
Ібупрофен,гель,98.75,30,false
Цитрамон,таблетки,32.20,12,false
Інсулін,розчин,520.00,90,true
"Вітаміни ""Сонечко"", дитячі",сироп,89.90,365,false
Нурофен,сироп,76.40,0,false
```

| Поле           | Тип після читання | Перетворення та правило                               |
|----------------|-------------------|-------------------------------------------------------|
| `name`         | `str`             | `strip()`, не порожнє                                 |
| `form`         | `str`             | `strip().lower()`, не порожнє                         |
| `price`        | `float`           | `float()`, скінченне, `>= 0`                          |
| `days_left`    | `int`             | `int()`, `>= 0`                                       |
| `prescription` | `bool`            | `true`/`false` без урахування регістру                |

Вимоги варіанта до даних виконано: 7 записів; дубльовані форми `таблетки` (ще й у різному
регістрі — `Таблетки`) і `сироп`; граничний запис `Ібупрофен` з `days_left = 30` (входить у
відбір) і нульовий `Нурофен` з `days_left = 0`; текстове поле з комою й лапками
`"Вітаміни ""Сонечко"", дитячі"`. Порожній результат відбору описано явно й перевірено
тестом: для порогу `--max-days 1` жоден запис, крім `Нурофен`, не відбирається, а для
файла лише з заголовком (`data/lab06-empty.csv`) відбір порожній.

Зафіксовані параметри: поріг `threshold = 30` (днів, ціле число; параметр `--max-days`);
дата не використовується — термін задано кількістю днів `days_left`.

Правило порожнього входу:

| Вхід                                   | Результат                                          |
|----------------------------------------|----------------------------------------------------|
| файл лише з заголовком                 | коректний порожній набір, звіт із нулями й «немає даних», код 0 |
| файл нульової довжини (немає заголовка) | `DataError: Рядок 1: файл порожній, відсутній заголовок CSV`, код 2 |

## 4. Структура модулів

```text
src/kzp_lab06/
├── __init__.py   версія пакета (__version__ = "1.5.0")
├── errors.py     DataError(ValueError)
├── loader.py     DictReader, перевірка заголовка, перетворення полів, iter_records/load_records
├── analysis.py   select_expiring, unique_forms, count_by_form, nearest_expiry,
│                 average_price, summarize(*metrics, max_days=30, **labels), make_summary
├── reporting.py  format_report (текст), write_report (with + Path.open)
└── cli.py        argparse, коди завершення, повідомлення в stderr, UTF-8 для консолі
```

Межі відповідальності: `loader` не рахує й не друкує; `analysis` не відкриває файлів і
повертає дані, а не текст; `reporting` не читає CSV; лише `cli` знає про `sys.argv`,
`stdout`/`stderr` і коди завершення. Під час імпорту жоден модуль не виконує дій: точка
входу — `main()` у `cli.py` під `if __name__ == "__main__":` і скрипт `kzp-lab06` у
`pyproject.toml`.

`pyproject.toml` описує пакет (`setuptools`, `src`-layout; локально зібрано з setuptools 84.2.1), `requires-python = ">=3.11"`,
dev-залежності `pytest`, `ruff`, `build`, скрипт `kzp-lab06`, налаштування pytest
(`testpaths = ["tests"]`) і ruff (`line-length = 88`, правила `E, W, F, I, B, UP`).
Залежностей часу виконання немає — лише стандартна бібліотека.

## 5. Перетворення даних і колекції

- Список — `load_records` повертає `list[dict[str, object]]` у порядку файла; відбір
  `select_expiring` — list comprehension
  `[record for record in records if int(record["days_left"]) <= max_days]`.
- Множина — `unique_forms`: set comprehension `{str(record["form"]) for record in records}`;
  повторні `сироп` і `таблетки` потрапляють туди один раз.
- Словник — `count_by_form`: dict comprehension за відсортованими формами
  `{form: sum(1 for ... if record["form"] == form) for form in sorted(forms)}`.
- Генераторні вирази — у `sum`, `min`, `sorted`; генератор `iter_records` повертає
  записи по одному (`yield`), а `load_records` лише збирає їх у список.

Comprehensions використано там, де є одне прозоре перетворення або відбір. Розбір
рядка (`parse_row`) і перевірка заголовка написані звичайним кодом, бо там кілька
умов і винятки.

## 6. Функції

```python
def summarize(
    records: list[Record],
    *metrics: str,
    max_days: int = DEFAULT_MAX_DAYS,
    **labels: str,
) -> dict[str, object]:
```

- `metrics` усередині — кортеж назв числових полів (`"price"`, `"days_left"`);
- `max_days=30` — типове значення; воно незмінне (`int`), тому не створює стану між
  викликами;
- `labels` — словник «метрика → підпис у результаті».

Приклад виклику і результат для `data/lab06.csv`:

```python
summarize(records, "price", "days_left", price="Сума")
# {'count': 4, 'Сума': 339.35, 'days_left': 67.0}
```

Невідома метрика (`summarize(records, "name")`) або підпис без метрики — `ValueError`,
навіть для порожнього входу: схема перевіряється за `NUMERIC_FIELDS`, а не за даними.
Якщо відібрано нуль записів, кожна метрика дорівнює `0.0`. Ці випадки перевірено тестами.

Типові параметри мають також `select_expiring(records, max_days=30)` і
`make_summary(records, max_days=30)`.

## 7. Алгоритм аналізу

1. Відбір: записи з `days_left <= max_days` (типово 30, межа включна).
2. Агрегування за ключем: кількість записів за формою (`count_by_form`) — для всіх записів.
3. Унікальні значення: множина форм (`unique_forms`).
4. Показники варіанта: найближчий термін — мінімальний `days_left` і всі препарати з ним
   (`nearest_expiry`); середня ціна всіх записів (`average_price`); додатково — кількість
   рецептурних і сумарна вартість відібраних (через `summarize`).

Детермінований порядок: ключі словника форм сортуються; відібрані препарати — за
`days_left`, при рівності — за назвою; назви з однаковим найближчим терміном — за
абеткою (кодовими точками Unicode); числа форматуються як `{:.2f}`. Тест перевіряє, що
звіт для переставлених рядків збігається з оригінальним.

Для порожнього списку `nearest_expiry` і `average_price` повертають `None` (ділення на нуль
не виконується), а `count_by_form` — порожній словник: сума для форми без записів не
створюється.

## 8. Обробка помилок

`DataError(ValueError)` — єдиний виняток для поганих вхідних даних. Повідомлення містить
номер рядка файла (заголовок — рядок 1) і назву поля; технічна причина зберігається через
`raise ... from error` і доступна в `__cause__`.

| Ситуація                          | Повідомлення (приклад)                                        | Причина (`__cause__`) |
|-----------------------------------|---------------------------------------------------------------|-----------------------|
| немає заголовка                   | `Рядок 1: файл порожній, відсутній заголовок CSV`             | —                     |
| відсутній стовпець                | `Рядок 1: відсутні стовпці: days_left`                        | —                     |
| зайвий стовпець                   | `Рядок 1: невідомі стовпці: color`                            | —                     |
| хибне число                       | `Рядок 3: поле price має бути числом, отримано 'ціна'`        | `ValueError`          |
| дробові дні                       | `Рядок 2: поле days_left має бути цілим числом, отримано '2.5'` | `ValueError`        |
| `nan`/`inf`                       | `Рядок 2: поле price має бути скінченним числом`              | —                     |
| від'ємне значення                 | `Рядок 2: поле price не може бути від'ємним`                  | —                     |
| хибна ознака рецепта              | `Рядок 2: поле prescription має бути true або false, отримано 'так'` | `KeyError`     |
| порожнє значення                  | `Рядок 2: поле name порожнє`                                  | —                     |
| рядок коротший за заголовок       | `Рядок 2: відсутнє значення поля days_left`                   | —                     |
| рядок довший за заголовок         | `Рядок 2: зайві значення поза заголовком`                     | —                     |
| файл не в UTF-8                   | `Файл … не в кодуванні UTF-8`                                 | `UnicodeDecodeError`  |
| файл не існує / недоступний       | `Не вдалося прочитати файл …`                                 | `OSError`             |

Голого `except` і `except Exception` у коді немає: кожен блок ловить конкретні типи.
Межа CLI перехоплює лише `DataError` і `OSError` під час запису; будь-яка інша помилка не
маскується порожнім звітом, а завершує програму з traceback.

Коди завершення CLI:

| Код | Коли                                                                 |
|-----|----------------------------------------------------------------------|
| `0` | звіт записано                                                        |
| `2` | помилка даних (`DataError`), неправильні аргументи (argparse), вихідний файл збігається з вхідним |
| `1` | звіт неможливо записати (`OSError`, наприклад шлях — каталог)        |

Перевірка в PowerShell:

```text
PS> python -m kzp_lab06.cli data\lab06.csv reports\summary.txt; $LASTEXITCODE
Звіт записано: reports\summary.txt (записів: 7)
0
PS> python -m kzp_lab06.cli data\lab06-invalid.csv reports\bad.txt; $LASTEXITCODE
Помилка даних: Рядок 3: поле price має бути числом, отримано 'ціна'
2
```

`cli.main` перемикає `stdout` і `stderr` на UTF-8, тому українські повідомлення
коректні й у консолі Windows.

## 9. Файловий звіт

- Шлях задає другий аргумент CLI (у прикладах `reports/summary.txt`); каталог
  створюється через `mkdir(parents=True, exist_ok=True)`; каталог `reports/` не
  додається до репозиторію.
- Запис: `with path.open("w", encoding="utf-8", newline="\n") as target:` — файл
  закривається навіть у разі винятку, кодування й закінчення рядків не залежать від ОС.
- Вхідний файл не змінюється (тест порівнює байти до й після читання); CLI відмовляється
  писати звіт у вхідний файл.
- Еталон: `data/lab06-expected-report.txt`; тест і CI порівнюють з ним результат.

## 15. Відповіді на контрольні питання

1. Описує пакет в одному місці: назву, версію, мінімальний Python, залежності (зокрема
   dev), бекенд збирання, консольний скрипт і налаштування pytest та ruff, тож локальна
   перевірка й CI користуються тим самим контрактом.
2. Щоб залежності проєкту не змішувалися з системними й іншими проєктами і їх можна
   було відтворити з `pyproject.toml` на будь-якій машині.
3. Щоб модуль `csv` сам обробляв закінчення рядків, зокрема перенесення всередині поля в
   лапках; інакше на Windows можуть з'являтися зайві `\r` або порожні рядки.
4. Словники `str → str`; відсутні значення короткого рядка — `None`, зайві значення —
   список під ключем `restkey` (`None`). Числа, дати й bool залишаються рядками.
5. Кома всередині лапок теж розірве поле, лапки не знімуться, а перенесення рядка в полі
   розіб'є запис.
6. Список — впорядкована послідовність із повторами й доступом за індексом; словник —
   відображення унікальних ключів у значення; множина — невпорядкований набір унікальних
   значень зі швидкою перевіркою належності.
7. Коли є одне просте перетворення або відбір. Якщо потрібні кілька вкладених умов,
   винятки, побічні ефекти чи накопичення стану, звичайний цикл читається краще.
8. `*args` — кортеж зайвих позиційних аргументів, `**kwargs` — словник зайвих іменованих.
9. Типове значення обчислюється один раз під час оголошення функції, тому змінений
   список чи словник «пам'ятається» між викликами.
10. Новий виняток отримує атрибут `__cause__` з первинним винятком; traceback показує
    обидва, тож видно і зрозуміле повідомлення, і технічну причину.
11. Кожен модуль має одну відповідальність, його можна тестувати окремо (аналіз — без
    файлів), а зміна формату звіту не зачіпає читання CSV.
12. Файл буде закрито (а буфер записано) при виході з блоку — і звичайному, і через
    виняток.
13. Щоб той самий вхід завжди давав той самий текст: його можна порівнювати з еталоном у
    тестах і CI та бачити справжні зміни в diff.
14. Файл нульової довжини (немає заголовка — помилка), файл лише з заголовком
    (порожній коректний набір), порожній відбір, відсутність ділення на нуль для середнього
    й мінімуму.
15. Тест поведінки перевіряє результат через публічний інтерфейс (повернені значення,
    файл, код завершення) і не ламається від рефакторингу; перевірка реалізації
    прив'язана до внутрішніх змінних і викликів.
16. Файли `test_*.py` або `*_test.py`, у них — функції `test_*` і методи `test_*` класів
    `Test*` (у цьому проєкті — лише в `tests/`).
17. `ruff check` — помилки й стиль: невикористані імпорти й змінні, порядок імпортів,
    довжину рядків, типові пастки (`B`), застарілий синтаксис (`UP`); `ruff format --check`
    — що код уже відформатовано.
18. `0` — успіх; `2` — помилка даних або аргументів; у цьому проєкті ще `1` — звіт
    неможливо записати.
19. Вони ловлять різне: тести — неправильну поведінку, ruff — помилки й стиль, які тести
    можуть не зачепити, пакетування — помилки опису пакета (не той каталог, відсутній
    модуль у wheel), яких не видно при запуску з вихідного коду.
20. Вхідний CSV і його заголовок, правила типів і порожнього входу, поріг відбору,
    повний очікуваний звіт, коди завершення, команди запуску, результати pytest, ruff,
    wheel і CI, посилання на артефакт і тег.

## 16. Висновки

Створено Python-пакет `kzp_lab06`, у якому завантаження CSV, аналіз, формування звіту й
CLI розділено на модулі. CSV читається стандартним `csv.DictReader` з явним UTF-8, п'ять
полів перетворюються на `str`, `float`, `int` і `bool` із перевіркою, помилки подаються
`DataError` з номером рядка й першопричиною. Аналіз побудовано на списку, словнику,
множині й comprehensions; функція `summarize` демонструє `*args`, типовий параметр і
`**kwargs`. Звіт детермінований і записується через `with`. Поведінку закріплено 45
тестами, якість — ruff, пакет збирається у wheel і перевіряється в CI на трьох ОС.
Функції аналізу над словниками стануть основою наступної роботи, де записи буде
перенесено на класи з `@dataclass` і `@property`.
